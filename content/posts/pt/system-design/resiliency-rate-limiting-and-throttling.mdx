Nós começamos uma série de artigos sobre padrões de resiliência. Vimos como o [Retry](/pt/blog/system-design/resiliency-why-retries-can-bring-down-your-system) recupera falhas transitórias, como o [Exponential Backoff e o Jitter](/pt/blog/system-design/resiliency-exponencial-backoff-in-practice) distribuem essas tentativas ao longo do tempo e como o [Circuit Breaker](/pt/blog/system-design/resiliency-circuit-breaker-when-should-you-stop-trying) decide quando é hora de parar de tentar.

Até aqui, o foco sempre foi o lado de quem chama: como um cliente deve se comportar quando uma dependência falha. Neste artigo a perspectiva muda para o lado de quem recebe as chamadas: como um serviço se protege quando chega mais tráfego do que ele consegue processar.

É aí que entram dois conceitos bastante importantes quando falamos de resiliência e controle de tráfego: Rate Limiting e Throttling. A ideia deste artigo é entender o que cada um faz, qual a diferença real entre eles e como aplicá-los nas nossas aplicações.

## Rate Limiting

Rate Limiting é uma técnica usada para restringir a quantidade de requisições que uma API pode receber. Definimos uma quantidade fixa de requisições que um cliente pode executar dentro de um determinado período de tempo, prevenindo abusos e protegendo os recursos dos nossos servidores.

Esse limite pode ser, por exemplo, de 1000 requisições por segundo, por minuto ou por dia. Quando ele é excedido, o cliente passa a receber um erro, geralmente `429 Too Many Requests`, informando que o limite foi atingido e que ele precisará aguardar até que sua cota seja restabelecida.

Uma implementação simples de rate limiting já traz um grande ganho de resiliência para a API e seus recursos, e também protege contra ataques de agentes maliciosos, que passam a ser bloqueados. No entanto, é extremamente importante configurar o limite ideal para cada cenário, e esse limite deve estar alinhado com as regras de negócio do serviço.

### O cliente também precisa estar preparado

Se o limite configurado é de 1000 requisições por segundo e acontece um aumento repentino de tráfego, todas as requisições excedentes serão rejeitadas. Isso exige que o cliente que chama a aplicação esteja preparado e seja resiliente o suficiente para realizar novas tentativas, aplicando do lado dele as técnicas que vimos nos artigos anteriores, como [Retry com Exponential Backoff e Jitter](/pt/blog/system-design/resiliency-exponencial-backoff-in-practice).

## Throttling

Throttling é um mecanismo de controle de fluxo. Assim como o Rate Limiting, ele controla a quantidade de requisições que uma API recebe durante um período de tempo. A diferença está no que acontece quando o limite é atingido: em vez de simplesmente rejeitar, ele regula a velocidade das requisições, podendo enfileirar, atrasar ou processar de forma mais lenta, para manter o sistema dentro de uma capacidade sustentável sem necessariamente descartar a chamada.

O objetivo é lidar com sobrecarga e tráfego inesperado mantendo o sistema estável, sem degradá-lo, e garantindo uma performance uniforme para os usuários. Como o volume que cada cliente consegue enviar é limitado temporariamente, os recursos não são consumidos por um único usuário em prejuízo de todos os outros. Desse modo, todos continuam acessando a API, sem serem prejudicados por uma parada completa do sistema.

### Nem tudo são flores

Implementar throttling também adiciona algumas limitações ao sistema. Durante picos de tráfego, o processamento fica mais lento e a latência aumenta, já que existe um limite configurado de chamadas para aquela API. No código, também aumentamos a complexidade da aplicação.

## A diferença entre os dois

No início, quando comecei a estudar essas duas ferramentas, eu entendia que elas tinham uma correlação direta e que eram obrigatoriamente usadas em conjunto. Mas as coisas não funcionam dessa forma.

Rate Limiting é a política: você define um limite fixo, por exemplo 1000 requisições por segundo ou 100 por minuto, e quando esse limite é estourado, a requisição excedente é simplesmente rejeitada.

Throttling trata o excesso de maneira graciosa, sem que necessariamente todas as próximas requisições sejam rejeitadas. Elas podem ter um processamento mais lento, ou ser enviadas para uma fila de espera até que as condições sejam atendidas.

**A diferença real é a reação quando o limite é atingido: throttling suaviza e atrasa, rate limiting corta e rejeita.**

|                  | Rate Limiting                            | Throttling                                   |
| ---------------- | ---------------------------------------- | -------------------------------------------- |
| Reação ao limite | Rejeita (`429`)                          | Atrasa, enfileira ou desacelera              |
| Objetivo         | Política fixa de uso                     | Controle de fluxo gracioso                   |
| Exemplo          | 100 req/s por usuário, 1000 req/s global | Reduzir a taxa quando o threshold é atingido |

## Algoritmos: Token Bucket e Leaky Bucket

Enquanto escrevia este artigo, percebi que algoritmos como Token Bucket e Leaky Bucket são frequentemente associados somente ao Rate Limiting. Eu entendia que, no momento em que escolhêssemos um desses algoritmos, estaríamos necessariamente falando de limite de taxa. Mas eles também podem ser utilizados para decidir quando o throttling deve acontecer.

Por exemplo, se configuramos na nossa aplicação um Token Bucket com capacidade de 1000 e todos os tokens foram consumidos, nesse momento podemos aplicar políticas de throttling e reduzir a taxa de processamento da API, em vez de usar rate limiting e rejeitar todas as requisições seguintes.

O algoritmo é o mesmo. O que define se o resultado é rate limiting ou throttling é o comportamento que desejamos para a aplicação:

- **Rate Limiting** impõe políticas de uso bem definidas.
- **Throttling** preserva a experiência do usuário sob alto volume de tráfego.

## Exemplos em Go

Os dois primeiros exemplos usam o pacote `golang.org/x/time/rate`, que implementa um Token Bucket. Repare que o limiter é o mesmo nos dois casos: só muda o que fazemos quando os tokens acabam.

### Rate Limiting: rejeita quando o limite é atingido

```go
import (
	"net/http"

	"golang.org/x/time/rate"
)

// 1000 requisições por segundo, com burst de 50
var limiter = rate.NewLimiter(1000, 50)

func rateLimitMiddleware(next http.Handler) http.Handler {
	return http.HandlerFunc(func(w http.ResponseWriter, r *http.Request) {
		if !limiter.Allow() {
			http.Error(w, "too many requests", http.StatusTooManyRequests) // 429
			return
		}
		next.ServeHTTP(w, r)
	})
}
```

`Allow()` consome um token se houver. Se o bucket estiver vazio, a requisição é rejeitada na hora com `429`.

### Throttling: espera e processa com atraso controlado

```go
import (
	"context"
	"net/http"
	"time"

	"golang.org/x/time/rate"
)

var throttler = rate.NewLimiter(1000, 50)

func throttleMiddleware(next http.Handler) http.Handler {
	return http.HandlerFunc(func(w http.ResponseWriter, r *http.Request) {
		ctx, cancel := context.WithTimeout(r.Context(), 5*time.Second)
		defer cancel()

		if err := throttler.Wait(ctx); err != nil {
			http.Error(w, "server busy, try again later", http.StatusServiceUnavailable)
			return
		}
		next.ServeHTTP(w, r) // processada com atraso controlado
	})
}
```

`Wait()` bloqueia até um token ficar disponível, então a requisição espera em vez de ser rejeitada. O timeout de 5 segundos evita que ela espere para sempre: passou disso, devolvemos `503`.

### Worker pool: throttling por concorrência

```go
package main

import (
	"fmt"
	"time"
)

type Job struct{ ID int }

func worker(jobs <-chan Job, results chan<- string) {
	for j := range jobs {
		time.Sleep(100 * time.Millisecond) // ritmo controlado de processamento
		results <- fmt.Sprintf("job %d processado", j.ID)
	}
}

func main() {
	jobs := make(chan Job, 100)
	results := make(chan string, 100)

	for w := 1; w <= 5; w++ {
		go worker(jobs, results)
	}

	for i := 1; i <= 20; i++ {
		jobs <- Job{ID: i} // se o buffer encher, quem envia bloqueia
	}
	close(jobs)

	for i := 1; i <= 20; i++ {
		fmt.Println(<-results)
	}
}
```

Aqui o limite não é de requisições por segundo, e sim de quantos jobs são processados ao mesmo tempo: no máximo 5, um por worker. O que passa disso espera no channel, e quando o buffer enche, quem envia fica bloqueado até um worker liberar espaço.

## Conclusão

{/* TODO: revisar quando o texto estiver fechado. */}

Rate Limiting e Throttling resolvem o mesmo problema, o excesso de tráfego, com reações diferentes. Rate Limiting corta e rejeita, impondo uma política de uso clara. Throttling suaviza e atrasa, preservando a experiência do usuário enquanto o sistema se mantém dentro da sua capacidade. Algoritmos como o Token Bucket servem aos dois: a escolha está no comportamento que queremos quando o limite é atingido.
